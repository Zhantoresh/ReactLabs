1 Variables and Data Types

const name = "Diana";
let age = 22;
let isActive = true;
const courses = ["React", "JavaScript", "CSS"];
const address = { city: "Almaty", street: "Abay 10" };

let middleName = null;      // intentionally empty value
let nickname;               // undefined — declared but not assigned

Primitive values: name, age, isActive, middleName, nickname — store the value itself.

Reference values: courses (array) and address (object) — the variable stores a reference to a memory location.

let vs const: let allows reassigning the variable, const does not (though if it's an object/array, its contents can still be mutated).

typeof null returns "object" — this is a historical bug in JS kept for backward compatibility.

JavaScript primitive types: string, number, boolean, undefined, null, bigint, symbol.

My insight I didn't expect typeof null to say "object" — it feels like a trap question. I also realized I've been using undefined and null almost interchangeably in my own code, but now I want to be more intentional: null when I'm the one deciding something is empty, undefined when it just hasn't been set yet.

2 Arrays

const numbers = [3, 7, 2, 10, 5];

const doubled   = numbers.map(n => n * 2);
const above5    = numbers.filter(n => n > 5);
const firstAbove5 = numbers.find(n => n > 5);
const sum       = numbers.reduce((acc, n) => acc + n, 0);
const has10     = numbers.includes(10);
None of these methods (map, filter, find, reduce, includes) mutate the original array — they all return a new value. You can confirm this by printing numbers again after all the operations: it stays the same.
My insight reduce was the one that took me longest to actually get comfortable with — map and filter felt intuitive right away, but reduce needed me to slow down and trace through the accumulator step by step. Once I did that on paper it clicked, and now I actually like how flexible it is — you can build a sum, an object, even another array out of it.

3 Arrays of Objects

const students = [
  { id: 1, name: "Anna", grade: 85 },
  { id: 2, name: "John", grade: 62 },
  { id: 3, name: "Sara", grade: 91 },
  { id: 4, name: "Mike", grade: 55 },
];

const passed        = students.filter(s => s.grade >= 70);
const names          = students.map(s => s.name);
const studentById3   = students.find(s => s.id === 3);
const topStudent     = students.reduce((best, s) => s.grade > best.grade ? s : best);
const average        = students.reduce((sum, s) => sum + s.grade, 0) / students.length;
const withStatus     = students.map(s => ({ ...s, passed: s.grade >= 70 }));
map combined with the spread operator { ...s, passed: ... } creates a brand new object for every student — the original students array is left untouched.
My insight Chaining ideas from task 2 and applying them to objects instead of plain numbers made everything feel more "real" — this is basically what working with API data looks like. The pattern { ...item, newField } inside map is something I can already see myself using constantly in React state updates.

4 Objects

const user = {
  id: 1,
  name: "Diana",
  age: 22,
  address: { city: "Almaty", street: "Abay 10" }
};

// read
user.name; user.address.city;

// change
user.age = 23;

// add
user.email = "diana@mail.com";

// remove
delete user.address.street;

// destructuring
const { name: userName, age } = user;
const { address: { city } } = user;
When destructuring with { name: userName }, the name property is read out, but it's assigned to a new variable called userName — the object's own field is not renamed.
My insight I always knew basic destructuring, but renaming a property while destructuring ({ name: userName }) was new to me — I used to just do const userName = user.name on a separate line. Nested destructuring ({ address: { city } }) also felt awkward at first, but it's genuinely shorter than writing user.address.city twice.

5 Values and References

let original = { name: "Alice", score: 10 };
let copy = original;
copy.score = 99;
// original.score also becomes 99!

let original2 = { name: "Alice", score: 10 };
let properCopy = { ...original2 };
properCopy.score = 50;
// original2.score stays 10

let user2 = { name: "Alice", address: { city: "Almaty" } };
let shallowCopy = { ...user2 };
shallowCopy.address.city = "Astana";
// user2.address.city also changes — spread only copies the top level!

let deepCopy = { ...user2, address: { ...user2.address } };
deepCopy.address.city = "Shymkent";
// now user2.address.city stays unchanged
Why this happens: objects in JS are stored by reference. copy = original doesn't copy the object itself, only the memory address — both variables point to the very same object.

{ ...original } creates a shallow copy: top-level properties are copied as values, but nested objects (address) are still a shared reference. To copy a nested object too, you need to spread it explicitly as well: { ...user, address: { ...user.address } }, or use structuredClone(user).
My insight This was the biggest "aha" of the whole refresher. I honestly didn't realize { ...user } only does a shallow copy — I assumed spread just "duplicates everything." Seeing the nested address.city silently change on both objects was a little unsettling, but now I understand why React docs are so strict about not mutating nested state directly.

6 Functions

// regular function
function isEven(number) {
  return number % 2 === 0;
}

// arrow version of the same function
const isEvenArrow = (number) => number % 2 === 0;

function getFullName(firstName, lastName) {
  return `${firstName} ${lastName}`;
}

const calculatePrice = (price, quantity) => price * quantity;

const calculateDiscount = (price, percent) => price - (price * percent) / 100;

const getMax = (a, b) => (a > b ? a : b);
My insight Rewriting a normal function as an arrow function made me notice how much shorter one-line logic becomes — no function keyword, no return, no braces. But I want to be careful not to overuse the super-short form when a function does something non-obvious; sometimes the explicit function syntax reads clearer for someone reviewing my code later.

7 Functions as Values

const add = (a, b) => a + b;
const multiply = (a, b) => a * b;

function calculate(a, b, operation) {
  return operation(a, b);
}

calculate(5, 3, add);       // 8
calculate(5, 3, multiply);  // 15

Yes, functions are first-class citizens in JS: they can be stored in variables and passed to other functions as arguments (this is called a higher-order function).

add is a reference to the function itself (it can be passed around without being called). add() is a call of the function, which immediately executes it and returns the result.

My insight I've written onClick={handleClick} vs onClick={handleClick()} mistakes before without fully understanding why one worked and the other didn't — now the add vs add() distinction from this task makes that old bug make complete sense. Passing the function itself, not its result, is the whole trick.

8 Scope

const message = "global";

function showScopes() {
  let message = "function";
  console.log(message); // "function"

  if (true) {
    let message = "block";
    console.log(message); // "block"
  }

  console.log(message); // "function" — the block didn't affect the function scope
}

showScopes();
console.log(message); // "global" — the function didn't affect the outer scope

if (true) {
  var varVal = "var value";
  let letVal = "let value";
  const constVal = "const value";
}
// varVal is accessible outside, letVal and constVal are not (ReferenceError)

Global scope — a variable visible throughout the whole file/script.

Function scope — a variable visible only inside the function where it was declared.

Block scope — a variable visible only inside the { } block (if, for, while, etc).

var ignores block scope (it's only limited by function scope or global scope), while let and const respect block scope. The difference between let and const is whether reassignment is allowed.

My insight Seeing var "leak" outside of the if block while let threw a ReferenceError made the difference concrete instead of just theoretical. I think this is exactly why var is considered outdated now — it's too easy to accidentally rely on a variable that "shouldn't" be accessible anymore.

9 Closure

function createCounter() {
  let count = 0;
  return function () {
    count += 1;
    return count;
  };
}

const counter = createCounter();
counter(); // 1
counter(); // 2
counter(); // 3

const counter2 = createCounter(); // separate counter, its own count
counter2(); // 1

function createAdder(value) {
  return function (num) {
    return num + value;
  };
}

const addFive = createAdder(5);
addFive(10); // 15
addFive(20); // 25
The inner function keeps access to the outer function's variables even after the outer function has finished executing — this is called a closure. Every call to createCounter() creates a brand new, independent count variable inside its own lexical environment, so counter and counter2 don't interfere with each other.
My insight This is the task that made useState stop feeling like magic. If a returned function can "remember" a variable from the function that created it, then a hook remembering state between renders isn't some special React trick — it's the same closure idea I just wrote by hand in createCounter.

10 Destructuring, Spread and Rest

const numbers = [10, 20, 30, 40];
const [first, second] = numbers;

const user = { id: 1, name: "Anna", age: 21 };
const { name, age } = user;

const withNewNumber = [...numbers, 50];
const olderUser = { ...user, age: 22 };
const userWithEmail = { ...user, email: "anna@mail.com" };

const arrA = [1, 2];
const arrB = [3, 4];
const combined = [...arrA, ...arrB];

function sum(...numbers) {
  return numbers.reduce((acc, n) => acc + n, 0);
}
sum(1, 2);       // 3
sum(1, 2, 3, 4); // 10
Spread (...) "unpacks" the elements of an array/object — used when building a new array/object or passing arguments. Rest (...) does the opposite — it collects an arbitrary number of function arguments into a single array. The syntax looks the same, but the meaning is opposite: spread expands, rest gathers.
My insight I used to think spread and rest were just "the same three dots," so mixing them up in my head made destructuring code confusing to read. Framing it as "spread is on the right side / rest is on the left side (or in parameters)" is the mental shortcut that finally made it stick for me.

11 Optional Chaining and Default Values

const userWithAddress = { name: "Anna", address: { city: "Almaty" } };
const userWithoutAddress = { name: "John" };

// userWithoutAddress.address.city -> TypeError: Cannot read properties of undefined

const cityA = userWithAddress.address?.city;         // "Almaty"
const cityB = userWithoutAddress.address?.city;      // undefined

const displayCityA = userWithAddress.address?.city ?? "City not specified";
const displayCityB = userWithoutAddress.address?.city ?? "City not specified";

// || vs ??
[0, "", false, null, undefined].map(v => ({
  value: v,
  or:      v || "fallback",
  nullish: v ?? "fallback",
}));
?. safely "short-circuits" a property access if the preceding value is null/undefined, returning undefined instead of throwing an error. ?? only substitutes a fallback value when the left side is null or undefined. ||, on the other hand, treats any falsy value as "empty" — so 0, "", and false also get replaced by the fallback, which is often not what you want. ?? is safer in those cases.
My insight The 0 || "fallback" case genuinely surprised me — I can already think of a past bug where a quantity of 0 got silently replaced by a default value because I used || instead of ??. This task basically explained a bug I didn't understand at the time.

★ Final Task

const students = [
  { id: 1, name: "Anna",  age: 20, grades: [85, 90, 78] },
  { id: 2, name: "John",  age: 21, grades: [60, 55, 65] },
  { id: 3, name: "Sara",  age: 22, grades: [91, 95, 89] },
  { id: 4, name: "Mike",  age: 20, grades: [50, 48, 60] },
  { id: 5, name: "Diana", age: 23, grades: [72, 80, 75] },
];

const getAverage = (grades) =>
  grades.reduce((sum, g) => sum + g, 0) / grades.length;

const getStudentAverage = (student) => getAverage(student.grades);

const getPassedStudents = (students) =>
  students.filter(s => getStudentAverage(s) >= 60);

const getStudentNames = (students) => students.map(s => s.name);

const findStudent = (students, id) => students.find(s => s.id === id);

const getTopStudent = (students) =>
  students.reduce((best, s) =>
    getStudentAverage(s) > getStudentAverage(best) ? s : best
  );

const summary = students.map(s => ({
  id: s.id,
  name: s.name,
  average: Number(getStudentAverage(s).toFixed(1)),
  passed: getStudentAverage(s) >= 60,
}));
All functions are pure: they don't mutate the students array or its objects — they return new values/arrays instead.
My insight Building this out of small, single-purpose functions (getAverage, getStudentAverage, getTopStudent...) instead of one giant block of code made it way easier to debug — when something looked wrong, I could test each function on its own instead of untangling one long script. This feels like the "component" mindset from React showing up already, just with plain functions.

Overall takeaways

Individual insights are noted under each task above. Zooming out, the two ideas that connect almost everything here are immutability — not mutating arrays/objects directly, always returning new ones via spread or array methods — and closures, which quietly power things like counters and, it turns out, React's useState. Going into React, I want to keep leaning on map/filter/reduce and spread by default, and stay suspicious of any code that looks like it's mutating something in place.
